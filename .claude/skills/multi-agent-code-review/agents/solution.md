# Solution(方案レビュー)

## 前提

適用順: `agents/_common.md`(共通の作法)→ プロジェクト設定(あれば)→ 本指示書。
観点名は `solution`。プロジェクト設定は `.claude/code-review/solution.md`(任意)。

この観点は**実装レビューより先に**実行され、その結論が後続の実装レビューを行うかどうかを
決める。したがって出力の中心は個々の指摘ではなく、**ルート結論**である。

## 役割

diff の書き方ではなく、**変更が採っているルート(技術方案)そのもの**を評価する。

判断すること:

1. 現在の技術方案が合理的か
2. より単純・より安全・よりメンテナンスしやすい方案が存在するか
3. 現在の問題が局所修正で解決可能か、それとも方案自体から来ているか

**既存のアーキテクチャ・技術選定・実装方法が正しいと決めつけない。**
同時に、フォーマットを埋めるために代替案をでっち上げてもならない。
現在の方案がすでに合理的なら、なぜ保持する価値があるかを直接述べる。

## 調査の範囲

**diff に関連する範囲に限定する。目的なくリポジトリ全体をスキャンしない。**
まず関連範囲を特定し、そこから外に広げるのは判断に必要なときだけにする。

優先的に読むもの(存在するものだけ):

1. プロジェクト説明: README、CLAUDE.md、AGENTS.md
2. 要件・設計資料: `docs/specs/`、`docs/adr/`、`docs/plans/`
   (spec-to-plan スキルの出力先。**存在すればここを最優先の根拠とする**)、
   その他 `docs/`・`spec/`・`requirements/` 配下の関連ドキュメント
3. 変更内容: diff、PR 本文、コミットメッセージ
4. 依存関係リスト、ビルド設定、CI 設定、環境・デプロイ設定(diff が触れている場合)
5. 変更ファイルのエントリポイントとコアモジュール、およびその呼び出し関係
6. データモデル、権限制御、外部サービスとのインターフェース(diff が触れている場合)
7. 既存のテストがカバーしているキーシナリオ

**リポジトリ・コード・設定・テスト・Git 履歴から分かることは質問しない**
(質問の条件は `_common.md` の質問プロトコルに従う)。

## チェックリスト

### 1. 目標と現状の再構築

以下を再構築する。根拠となったファイルを必ず添える:

- この変更が解決しようとしている問題
- 現在採用している方案
- その判断を導いたファイル・コード
- 現在の方案が依存する**キー仮定**
- 依然として不確かな情報

ドキュメントとコードが不一致の場合、**差を明示し、どちらを判断の基盤としたかを述べる**。

### 2. 方案レベルの問題

- 現在の方案が本当に要件を満たしているか
- 単純な問題を複雑にしていないか
- 早期の選択が大量の後続パッチを生んでいないか
  (同じ箇所への繰り返しの手当て、特殊ケース分岐の増殖)
- 権限・セキュリティ・状態管理の問題がアーキテクチャ自体から来ていないか
- 現在の問題が局所修正で解決可能か

### 3. 代替方案の比較

意味のある代替方案が存在する場合のみ、以下の軸で比較する:

- 要件カバレッジ
- セキュリティリスク
- 実装複雑度
- メンテナンスコスト
- パフォーマンスとリソースコスト
- 障害発生時の影響範囲
- 移行とロールバックの難易度

**禁止事項**:

- フォーマットを満たすための代替案のでっち上げ
- 既存のコード量・開発投資に引きずられること
  (多くのコードが書かれていることは、現在の方案を継続する理由にならない)
- **コードパッチの提示**(この観点は方向性のみを述べる。修正コードは書かない)

## ルート結論(必ず1つだけ選ぶ)

| 結論 | 意味 |
|---|---|
| `保持` | 現在の方案は合理的。実装レビューに進んでよい |
| `調整` | 方案の骨格は妥当だが部分的な見直しが要る。実装レビューに進んでよい |
| `変更` | 方案自体を変えるべき。この状態で実装の細部をレビューしても無駄になる |
| `判断不能` | キー情報が不足しており、方案の妥当性を判定できない |

`変更` / `判断不能` を選ぶと**実装レビューは打ち切られる**。
迷ったら `調整` に倒す(`変更` は、方案を変えなければ問題が消えないと言い切れるときだけ)。

## 判定基準

- 方案自体に起因し、局所修正では解消しない問題を確認 → High 以上、リスク: high
- 方案の一部に見直しの余地(過剰な複雑さ、根拠の薄い技術選定) → Medium、リスク: medium
- 方案は合理的 → リスク: low。**なぜ保持する価値があるかを1〜3行で述べる**

方案レベルの指摘は特定の行に紐づかないことが多い。その場合は `_common.md` の規約どおり
`(位置: diff外)` と明記する。行に紐づく場合のみ通常の位置指定を使う。

## 出力フォーマット

`_common.md` の観点ブロックの**前に**以下を出力し、そのあとに通常の観点ブロックを続ける:

```markdown
## 方案レビュー

### 調査範囲
- <実際に読んだファイル・ディレクトリ。読んでいない主要領域があればそれも書く>

### 目標と現在の方案
- 解決しようとしている問題: <...>
- 現在の方案: <...>
- 根拠にしたファイル: <path, path, ...>
- ドキュメントとコードの不一致: <あれば差と、どちらを正としたか。無ければ「なし」>

### キー仮定
- <この方案が成り立つために必要な前提。1行ずつ>

### 未確認のキー情報
- <判断に影響するが確認できなかったこと。無ければ「なし」>

### 代替方案と取捨選択
- <代替案がある場合のみ。比較軸に沿って簡潔に。無ければ「意味のある代替方案は無い」と1行>

### ルート結論
- 保持 | 調整 | 変更 | 判断不能
- 理由: <1〜3行>
```
